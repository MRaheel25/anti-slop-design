# Intake — UI / App Screen

Ask ALL questions in ONE message. Do not design with gaps. Record
unanswered items as explicit assumptions to confirm, never as silent
inventions. Required questions are marked [R].

## Universal (every type)

- [R] What is it for — what is the one action the viewer should take
  after seeing this?
- [R] Who is it for (audience, age, context, where they will meet it)?
- [R] Where will it be seen (sizes, surfaces, light and dark contexts)?
- [R] What exists already (brand, logo, colours, fonts, photos, copy)?
  Attach files or links.
- [R] What must it NOT look like, and who are the competitors to
  differ from?
- [R] What is the deadline and the deliverable format (file types,
  sizes, variants)?
- What is unknown — and who can answer it?

## UI-specific

- [R] Platform and devices: iOS, Android, web, desktop — and which
  screen sizes matter most?
- [R] The user task and the flow — map the steps: onboarding, core
  action, success, empty, and error states. Which screens are in
  scope, exactly?
- [R] Existing design system or components: shadcn/ui, Material,
  custom, none? Attach the system or its link.
- [R] Data — real content examples and edge cases: long names, empty
  lists, errors, offline, loading, no permission. Supply examples.
- Accessibility bar: WCAG AA, touch targets, colour independence?
- Motion expectations: subtle, expressive, none — and what motion
  must communicate (state change, hierarchy, continuity)?
- What the *shipped* references are: 3 apps the user admires, and
  why each one — for a named dimension, not "it looks nice".
- Who builds it, in what stack, and what component library will be
  used to implement it?
- What is out of scope — settings, admin, billing, notifications —
  so the flow does not silently grow?

## How to ask

One message, numbered, plain language. A UI without a task, a flow,
real data, and edge cases is a screenshot, not a product. Get those
four before researching. A screen with no empty state and no error
state is unfinished.
